# Playwright E2E test suite for health coaching SaaS

A 94-test Playwright suite covering public marketing pages, the coach portal (demo mode), the client portal (demo mode), and white-label config verification. No production code was touched; this is purely additive test infrastructure. The suite imports values from `site.config.ts` rather than hardcoding strings, making it white-label aware. All portal tests use `?demo=true` to bypass authentication.

Watch for: several coach and client portal tests that verify only page-level chrome (heading/sidebar renders) rather than actual feature behavior because demo mode doesn't hydrate data for those routes (confirmed); a placeholder Supabase key in the webServer config that could confuse future contributors about auth posture (confirmed); and a test ("coach feedback text is visible") whose assertion duplicates an earlier test in the same describe block, providing no additional signal (confirmed).

## High-level view

The infrastructure is Playwright 1.60 on Chromium with the dev server auto-started via `webServer` config. The env block injects a `CLIENT_ID` to select the tenant config and placeholder Supabase credentials to prevent the client from throwing at import time — tests run against a real Next.js dev server but with no backend connectivity, so pages that fetch from Supabase show loading spinners or empty states.

Public page tests (F1–F8) are the strongest part of the suite. They walk multi-step flows (pricing wizard, enquiry form) and assert config-driven text at each stage, exercising real user interactions that give genuine confidence the marketing funnel renders correctly across tenant configs.

Coach and client portal tests split between rich assertions (dashboard demo data, habits checkbox interactions, check-in submit flow) and thin "page loads" checks where demo mode doesn't populate data. The thin tests guard against route crashes but don't verify business logic, creating a false sense of coverage when reading test counts alone.

Every `beforeEach` uses `waitForLoadState("networkidle")`, which is a latent fragility — if the app adds WebSocket-based features or real-time polling, the 500ms idle threshold will cause flaky timeouts across the entire suite.

## Duplicate and low-signal assertions in the client home suite

In `client-portal.spec.ts` F16, the test "coach feedback text is visible" contains this assertion:

```ts
await expect(
  page.getByText(/check-in/i).first()
).toBeVisible();
```

This is byte-for-byte the same check as the preceding "quick action links exist" test. The comment explains the intended behavior — the demo data lacks a `created_at` field so the feedback card doesn't render — but instead of testing something else (like the fallback "Submit Weekly Check-in" link text specifically), it falls back to the same regex. A regression in the feedback rendering path would not be caught, while the green bar suggests it is.

## Demo mode coverage gaps across portals

The coach portal tests for F11–F15 and the client profile test (F22) amount to "does the page crash?" checks. F14 (Coach Check-ins) asserts only that the sidebar brand name renders — nothing about check-ins. F12 and F13 verify the "New Plan" / "New Workout" link href, useful as a smoke test but not exercising feature behavior.

The risk is that "22 coach portal tests passing" reads as full coach coverage. If demo data is later added to these routes, the existing tests won't validate it renders correctly — new tests would need to be written anyway.

## networkidle as universal wait strategy

Every `beforeEach` across all four spec files uses `waitForLoadState("networkidle")`. Playwright's `networkidle` waits for 500ms with no network requests. In a Next.js dev environment with HMR WebSocket connections, the HMR socket's periodic pings can keep the network "active" intermittently. Tests pass today because the ping interval exceeds 500ms, but this is a time bomb.

The pricing and enquiry multi-step tests also call `waitForLoadState("networkidle")` mid-flow after clicks — those are client-side state transitions with no network activity, so the waits add 500ms of dead time per step without providing stability.

## App-level finding: demo param inconsistency

The tests for F12 and F13 assert:

```ts
await expect(newPlanLink).toHaveAttribute("href", "/coach/plans/create");
await expect(newWorkoutLink).toHaveAttribute("href", "/coach/workouts/create");
```

These links don't append `?demo=true`, meaning clicking "New Plan" while in demo mode navigates to a page that requires authentication. The sidebar links correctly use a `useDemoSuffix` hook, but in-page action links are hardcoded. This is an app bug surfaced by the tests, not a test defect.
