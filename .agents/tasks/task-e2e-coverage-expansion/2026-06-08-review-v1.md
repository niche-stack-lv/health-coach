# E2E coverage expansion for coach and client portal pages

This change adds ~90 new E2E tests across two new files (`coach-pages-extended.spec.ts`, `client-pages-extended.spec.ts`) and expands three existing files to fill gaps in the F1-F24 test spec. It covers 12 previously-untested coach pages and 4 client pages, all exercised through the app's `?demo=true` mode which renders hardcoded mock data without requiring a real Supabase backend. The approach is purely additive — no application code was modified.

**Watch for:** Several assertions rely on brittle CSS class selectors (`.bg-gold\\/10`, `.ring-gold\\/20`, `.rounded-full.h-1`) that will silently pass or break on unrelated styling changes without catching actual regressions (confirmed). A few tests assert nearly nothing meaningful — checking that `body` is visible or that a bare `svg` element exists provides no regression signal (confirmed). The FAQ test's `domcontentloaded` workaround for Google Drive iframes is fragile and may produce flaky results in CI depending on network timing (likely).

## High-level view

The new coach test file is the bulk of the change: 413 lines covering daily check-ins, diet templates (list, edit, assign), dishes (list, edit), client detail, client adherence, workout templates (list, edit), and plan/workout creation. Each page gets a `describe` block with 3-7 assertions against demo data. The pattern is consistent — navigate with `?demo=true`, wait for `networkidle`, assert headings and known mock text. Where pages don't support demo mode (client detail), the test degrades to verifying the sidebar renders.

The client extension file covers food check-in (well-tested with real form assertions), FAQ (forced to use `domcontentloaded` due to external iframes), onboarding (renders fully in demo mode), and change-password (auth-gated, only verifies spinner). The FAQ and change-password sections represent the weakest coverage — they verify the page doesn't crash rather than testing behavior.

The existing file expansions are small targeted additions: skipped auth tests as documentation (F2-F4), payment form validation (F5), enquiry multi-step navigation (F6), QR image check (F7), demo links (F8), and CSS variable/class assertions for the color theme (F24).

<details>
<summary>Issues (5)</summary>

1. **CSS-class assertions are untethered to behavior** — Tests using `.bg-gold\\/10`, `.ring-gold\\/20`, `.rounded-full.h-1`, `.text-gold`, `.gradient-gold`, `.text-gradient-gold` will break on any Tailwind refactor without catching actual rendering bugs. Prefer semantic locators or visual regression tools for styling checks.
2. **Low-signal assertions in change-password and F19** — Asserting `body` is visible or `svg` exists provides zero regression value. Either assert something meaningful (the spinner text, a specific aria attribute) or remove the test.
3. **FAQ iframe flakiness risk** — Using `domcontentloaded` + explicit `waitFor` on the heading is reasonable, but `toBeAttached()` on iframes may be timing-sensitive if the DOM mutates during hydration. Consider adding a short timeout or retry.
4. **Overly broad text matchers** — `page.getByText(/cal/i).first()` will match the brand name "Cal" or any word containing "cal". The `.first()` suppresses the ambiguity but means the assertion might pass for the wrong reason.
5. **`siteConfig` import not validated** — Tests import `siteConfig` but never guard against undefined fields (e.g., `siteConfig.programs || []` appears but `siteConfig.aboutPlatform?.features` relies on optional chaining at test time). If the config shape changes, failures will be cryptic type errors rather than clear test failures.

## CSS-class selectors as behavioral assertions

The F24 color theme tests and the FAQ video card counts both hinge on Tailwind utility classes as their primary locators. In `config-verification.spec.ts`, the tests check for `.gradient-gold`, `.text-gradient-gold`, and `.text-gold` on the active nav. These are implementation details of the styling system, not user-visible behavior. If the design system switches from utility classes to CSS modules, or if the class is renamed to `text-brand`, all four F24 tests break without any visual regression actually occurring.

The same pattern appears in `client-pages-extended.spec.ts` where FAQ card counts use `.bg-gold\\/10` and `.ring-gold\\/20`:

```typescript
const videoIcons = page.locator(".bg-gold\\/10");
const count = await videoIcons.count();
expect(count).toBeGreaterThanOrEqual(10);
```

A more durable approach would be to use `data-testid` attributes, ARIA roles, or at minimum combine the class selector with a content assertion. The computed-style check for `--gold` CSS variable in the first F24 test is actually the strongest of the group — it verifies the theming mechanism works regardless of which classes consume it.

## Low-value assertions that will never fail

The change-password test asserts `body` is visible and checks that no element matches a regex for "error". The `body` assertion cannot fail on any page that loads at all. The error-text check uses `page.locator("text=/error|Error|ERROR/")` which is a pseudo-selector that Playwright resolves against `textContent` — but this would also match words like "errorless" or text inside hidden elements.

Similarly, the F19 habits "progress indicator exists" test:

```typescript
await expect(page.locator("svg").first()).toBeVisible();
```

This asserts that any SVG exists anywhere on the page. Every page with a Lucide icon passes this test. It provides no information about whether the progress indicator specifically rendered.

## FAQ iframe timing

The `beforeEach` for FAQ drops to `domcontentloaded` and then explicitly waits for the heading. The subsequent test that checks `iframes.first().toBeAttached()` could be sensitive to hydration timing — if React re-renders the component tree, iframe elements might briefly detach and reattach. In CI with slower machines or network variability, this pattern could surface intermittent failures.

## Broad text matchers hiding false positives

Several tests use extremely broad matchers with `.first()`:

```typescript
await expect(page.getByText(/cal/i).first()).toBeVisible();
await expect(page.getByText("1").first()).toBeVisible();
await expect(page.locator("text=/\\d+/").first()).toBeVisible();
```

The "1" assertion in F16 ("check-in count shows 1") matches the first occurrence of the digit "1" anywhere on the page — in dates, counts, version numbers, or even the brand name if it contains "1". The regex `\\d+` assertion in F17 ("daily macro totals calculate") matches any number anywhere. These tests document the intent but provide negligible regression protection. A more targeted approach would use a parent container locator chained with the text assertion.
